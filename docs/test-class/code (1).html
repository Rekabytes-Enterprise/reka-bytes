1. The Vibe Coding Mindset

🎯 Why this matters: If you try to learn vibe coding like traditional CS, you’ll quit in 2 weeks. This mindset shift is what makes everything else click.

Analogy: Chef vs. Food Critic

A traditional developer is a chef who memorizes every recipe. A vibe coder is a food critic who knows exactly what good food tastes like, can describe what’s wrong, and can direct the chef (AI) to fix it. You don’t need to cook — you need to taste and direct.

Traditional Developer Vibe Coder (You)
Memorizes syntax Recognizes patterns & describes intent
Writes code from scratch Generates, reviews, and refines
Fears the terminal Uses terminal as primary feedback loop
"I need to learn React first" "I need to understand state to fix this bug"

The Three Rules

  1. Never trust AI blindly. AI is confident even when wrong. Always verify.
  2. Read > Write. You must read code fluently even if you can’t write it from memory.
  3. Context is King. AI fails without context. Your job is to feed it the right information.
✅ Self-Check (No coding needed!) 1. If AI gives you code that looks correct but doesn’t work, what should you do first?
2. True or False: You need to memorize JavaScript syntax to be a vibe coder.
3. What is YOUR role when working with AI? (Hint: Not typist)

2. Your Workbench: IDE & Terminal

🎯 Why this matters: Bolt/Lovable are training wheels. VS Code + Terminal is the real bicycle. This chapter removes the fear of both.

Analogy: Workshop vs. Swiss Army Knife

Bolt/Lovable is a Swiss Army knife — portable, limited. VS Code is a full workshop — every tool on the wall, unlimited power. The terminal is just text messaging your computer: you type a command, it replies with text.

What the Terminal Actually Looks Like

$ cd my-project $ npm run dev ▲ Next.js 14.2.3 ✓ Ready in 2.1s ○ Local: http://localhost:3000 ○ Network: http://192.168.1.5:3000 $ _

This is NOT scary. It’s just your computer talking back. Green/white text = good. Red text = needs attention.

Essential Commands (Only These 8)

Command Plain English When to Use
pwd "Where am I?" When you’re lost in folders
ls "Show me files here" See what’s in current folder
cd folder "Go into this folder" Navigate deeper
cd .. "Go up one level" Go back to parent folder
npm install "Download project plugins" First time opening a project
npm run dev "Start the app" Run your project locally
cat file.txt "Show file contents" Quick peek at a file
Ctrl+C "Stop current command" Kill running server / cancel
🚫 Beginner Mistake #1 Typing commands in the wrong folder. Always run pwd first to confirm where you are before running anything destructive.
✅ Self-Check 1. You opened a new project. What command runs FIRST?
2. Your dev server is running and you want to stop it. What do you press?
3. You’re not sure which folder you’re in. What command tells you?

3. Mental Models: How Software Works

🎯 Why this matters: When AI generates broken code, understanding these models lets you spot WHERE it broke instead of guessing.

The Restaurant Analogy (Expanded)

Concept Restaurant In Your App If It Breaks…
Frontend Dining room Buttons, forms, pages UI looks wrong / nothing happens on click
Backend Kitchen Data processing, auth 500 error / data missing
Database Pantry User data, posts Empty results / save fails
API Waiter URL endpoints 404 / wrong data format
HTTP Request Order ticket fetch() / axios call Network tab shows failure

Client vs. Server: The Security Line

🚫 Beginner Mistake #2 Putting API keys, passwords, or database queries in frontend code. Anything in the browser is PUBLIC. Secrets ALWAYS live on the server.

Tech Stack Decision Tree

Don’t guess. Ask yourself ONE question: "What am I building?"

  • Simple dashboard / internal tool → Streamlit or Bolt
  • Web app with users + login → Next.js + Supabase
  • Blog / portfolio → Astro or plain HTML
  • Mobile app → React Native / Expo
  • Automation script → Python
✅ Self-Check 1. Your app shows a blank page. Is this likely a frontend or backend problem?
2. Your API returns a 500 error. Where should you look for logs?
3. You’re building a user login system. Should the password check happen in the browser or server?

4. Reading Code Without Writing It

🎯 Why this matters: AI writes code. YOU verify it. Reading is the verification skill. You don’t need to write a single line to be effective.

Analogy: Reading Sheet Music vs. Playing Piano

You don’t need to play piano to hear when a note is wrong. Similarly, you don’t need to write code to see when logic is broken. Focus on pattern recognition, not syntax memorization.

The 4 Patterns You Must Recognize

// PATTERN 1: IF/ELSE → Decision fork
if (user.isLoggedIn) {     // ← Condition (the question)
  showDashboard();         // ← YES path
} else {
  redirect('/login');      // ← NO path
}

// PATTERN 2: MAP → Transform each item
const names = users.map(user => user.name);
// Read as: "For EACH user → extract name"

// PATTERN 3: FILTER → Keep matching items only  
const active = users.filter(u => u.isActive);
// Read as: "KEEP only users where isActive = true"

// PATTERN 4: TRY/CATCH → Safety net
try {
  await fetchData();       // ← Risky thing
} catch (error) {
  showError(error);        // ← Plan B if it fails
}

Scope: The Bedroom Rule

Variables declared inside {} are trapped there. Like items in a bedroom — they don’t exist in the hallway. 

function greet() {
  let message = "Hello";   // ← Lives INSIDE this function
  console.log(message);    // ✅ Can see it here
}
console.log(message);      // ❌ UNDEFINED — not in this "room"
🚫 Beginner Mistake #3 Seeing undefined and assuming the variable was never created. 80% of the time, it exists but is in the wrong scope. Check the curly braces {}.
✅ Self-Check 1. You see users.map(...). In plain English, what is this doing?
2. A variable returns undefined. What should you check FIRST?
3. Code inside catch(error) runs when…?

5. Debugging: The Core Skill

🎯 Why this matters: This is THE most important chapter. AI will break things constantly. Debugging is how you unbreak them. This skill alone separates users from developers.

Analogy: Doctor Diagnosis

A patient says "my stomach hurts." A bad doctor prescribes pills immediately. A good doctor asks questions, runs tests, checks vitals. Debugging is diagnosis. Never guess — gather evidence first.

The 5-Step Diagnostic Order

  1. Read the EXACT error message (terminal/console) — copy it fully
  2. Check Network tab — did the request go out? What came back?
  3. Add strategic logs — trace data flow step by step
  4. Paste evidence to AI — error + code + what you tried
  5. Verify the fix — don’t accept blindly; test it

What Browser DevTools Actually Looks Like

Elements | Console | Sources | Network | ... ───────────────────────────────────────────── > POST /api/login 500 (Internal Server Error) ⏱ 243ms ↑ 1.2KB ↓ 89B Headers | Payload | Response | Timing Response: {"error":"Invalid credentials"} ─────────────────────────────────────────────

Open with F12 or Right Click → Inspect. The Console shows errors. The Network tab shows requests.

Status Code Quick Decode

Code Plain English Your Next Step
200 "All good" Problem is elsewhere
400 "You sent bad data" Check your payload/format
401 "Who are you?" Log in / refresh token
404 "That doesn’t exist" Check URL spelling
500 "Server crashed" Check BACKEND logs, not frontend
CORS "Browser blocked this" Server config issue, not your code
🚫 Beginner Mistake #4 Saying "it doesn’t work" to AI. Always provide: exact error + relevant code + what you expected. Vague prompts get vague fixes.
✅ Self-Check 1. You get a 500 error. Should you debug frontend or backend code?
2. What key opens DevTools in most browsers?
3. Before asking AI for help, what should you ALWAYS copy first?

6. Git: Save Points, Not Memorization

🎯 Why this matters: Without Git, one bad AI edit can destroy hours of work. With Git, you can always rewind. Think save points, not computer science.

Analogy: Video Game Saves

Before a boss fight, you save. If you die, you reload. Git commit = save point. Branch = alternate timeline. Push = cloud backup. That’s it.

Only 5 Commands You Need

Command Game Equivalent When
git pull Load latest save Before starting work
git add . Select changes to save Before committing
git commit -m "msg" Create save point After completing a task
git push Upload save to cloud After committing
git reset --soft HEAD~1 Undo last save (keep changes) Bad commit message / forgot files
🚫 Beginner Mistake #5 Committing .env files or API keys. Once pushed to GitHub, secrets are PUBLIC FOREVER even if deleted later. Always use .gitignore.
✅ Self-Check 1. You just finished adding a login form. What 3 commands run in order?
2. You made a bad commit. How do you undo it WITHOUT losing code?
3. What file prevents sensitive files from being committed?

7. AI Prompting Patterns for Debugging

🎯 Why this matters: The difference between a 30-second fix and a 3-hour rabbit hole is HOW you ask. This template works every time.

The Universal Debug Prompt Template

CONTEXT: [App type] + [Tech stack]
PROBLEM: [Symptom, NOT assumption]
ERROR:   [FULL error message pasted verbatim]
CODE:    [Relevant snippet ONLY]
TRIED:   [What you already attempted]
GOAL:    [Expected behavior]

Real Example: Bad vs. Good

❌ Gets Vague Answer ✅ Gets Precise Fix
"Login broken fix it" "Next.js 14 + Supabase. Login spinner never stops. Console: POST /api/auth 500. Checked Supabase creds — valid. Curl also returns 500. Goal: redirect to /dashboard on success."

Post-Fix Verification Questions (ALWAYS Ask)

  • "Explain WHAT changed and WHY."
  • "What edge cases could still break this?"
  • "Is any part of this deprecated?"
🚫 Beginner Mistake #6 Accepting AI code without asking it to explain. If you don’t understand the fix, you won’t be able to debug the NEXT bug it creates.

2. After AI fixes something, what should you ALWAYS ask?
3. True or False: "Fix this" is an acceptable debug prompt.
